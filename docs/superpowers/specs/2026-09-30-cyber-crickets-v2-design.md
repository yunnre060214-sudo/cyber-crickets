## 一、升级目标与已有约束

用户要求将整个项目从 1.0 进化到 2.0。结合现有项目定位，建议将其建设为完整的算法竞技平台：选策略与地图、观看对抗、举办赛事、回放关键过程、用批量实验验证强弱，形成一个连续的使用流程。

成功标准是出现实质性的新能力，并且这些能力共享同一套可复现的引擎与数据，而非独立拼接几个面板。2.0 应同时改善策略差异、观战信息、长期赛事管理和发布可靠性。

已有约束继续保留：

1. 纯前端、vanilla JavaScript、无需运行时后端，继续部署到现有 GitHub Pages 地址。
2. 默认浅色界面，直角、细分隔线、扁平、小字号，保持数据密度；所有主要功能适配手机。
3. 人类负责配置与观察，Agent 自动决策；相同条件下各方获得相同公开信息和行动机会。
4. VP、即时 reward、实时局势估计和历史样本胜率分别定义；算法名称与实际实现一致。
5. 保留种子、出生轮换、60/90/120/180 秒、10～1800 秒自定义时长、0.25×～20×播放速度及三种战报导出。
6. 发布验收以线上实际产物为准：代码、资源版本、README、仓库完整性、Actions 测试/上传/部署和线上版本均须核对。

本草案的默认判断：重点选择“完整竞技平台”。前述方向选择尚未得到用户回答，不能将其写成用户已经确认的偏好。

## 二、当前基线及可核查的缺口

当前版本已经有 18 个策略、六种赛制、模块化 UI、HTML/Markdown/JSON.gz 导出。「最强」已是 v6 规划器；其已有评测属于固定样本结果，不等同于所有地图上的强度结论。

| 核查结果 | 当前实现 | 2.0 要解决的实际问题 |
| --- | --- | --- |
| 单局计算与绘制在主线程 | `app.js` 的动画循环直接调用 `match.step(.035)` | 快速模拟、长期对局与 UI 响应共用执行时间 |
| 时间与决策调度依赖外部步长 | `nextDecision = time + .085` | 不同调用步长会改变实际决策时刻与得分 |
| 候选动作按已占格子抽样 | `Match.options()` 最多扫描约 300 个己方格 | 大领地不保证暴露全部合法前沿；候选生成消耗世界 RNG |
| 赛事固定八人 | `validate()`、固定分组与轮次常量 | 无法容纳不同规模的完整赛事 |
| 赛事保存以赛果为主 | `runDuel()` 保存 VP、翻色、终局领地 | 赛事中的精彩对局无法直接在平台回放 |
| 完整日志没有恢复所需状态 | `buildFullData()` 的说明明确不含 RNG 内部状态 | 导出数据不能作为可恢复的运行中存档 |
| 曲线将高分截在上限 | `Math.min(value,maxVP)`，`maxVP = duration × 2.5` | 高于标定值的真实差距在图上被压平 |
| 样式仍保留多轮补丁 | 10 个 CSS 模块、2808 行、222 处 `!important` | 模块拆分后仍存在大量覆盖关系 |
| 发布上传整个仓库 | Pages artifact 的 `path: .` | 七个历史入口副本、测试与评测数据也进入发布产物 |

时间调度实测：同一个 `v2-audit` 种子、四方阵容、10 秒比赛，`dt=.035` 时各方决策 95 次，前两次间隔 .105 秒；`dt=.05` 时各方决策 100 次，间隔 .1 秒，并且 VP 与前者不同。此结果证明当前引擎的确定性依赖固定调用步长，不能声称任意步长都得到同一结果。现有浏览器与赛事通常都使用 .035，不能据此宣称当前所有倍速会改变结果。

基线检查：完整单进程测试报告 69 项，其中 68 项通过，1 项因当前执行环境禁止 `execFileSync` 启动 Node 子进程而报 `EPERM`；该项涉及的 12 个文件分别执行 `node --check` 均通过。GitHub 上该基线的最新 Pages workflow 已 success。没有将环境限制归咎于产品语法错误。

已通过 Git blob SHA 对照确认本地核查副本的 57 个文件与该基线逐字一致。

## 三、方案取舍

| 方案 | 实质变化 | 取舍 |
| --- | --- | --- |
| A：完整竞技平台，推荐 | 共享新引擎，连通竞技场、赛事、回放和实验室，增加地图与策略生态 | 覆盖用户要求的整个项目；必须先建立时间、数据和版本边界 |
| B：观战娱乐优先 | 大幅增加地图事件、表现与局势变化 | 能快速丰富每局体验，但长期强度比较与赛事记录仍薄弱 |
| C：策略实验室优先 | 强化调试、批量对照、统计与策略接口 | 适合研究算法，普通观战者感知到的玩法进化较少 |

建议采用 A。B 的内容选用可公开、可复现的地图和资源轮换机制，C 的内容选用可在浏览器运行的批量实验；将其纳入同一条比赛数据链。

## 四、2.0 的产品范围

### 4.1 竞技场与地图

同时提供 1v1 和四方对抗，默认仍为四方。新增四种 64×64 地图模板：

1. 平衡平原：旋转对称的地形与资源分布，作为标准竞技与算法比较入口。
2. 中央盆地：中心高价值节点与较难进入的地形，强调抢中心和保有能力。
3. 双轴峡谷：明确的不可通行格与通道，形成绕行、堵口和反抢位置。
4. 环形走廊：多条环状通路与分散资源，强调路线选择和多线扩张。

四方地图采用四角旋转对称，单挑地图采用两侧对称。地图生成结束后检查所有出生核心、全部资源和通路的连通性。不可通行格不能作为动作目标，领地计分分母使用可通行格总数。核心区始终受保护。

标准控制开局生成 32 个对称资源节点，其中 24 个价值 1、8 个价值 3；33% 赛程增加 12 个价值 1 的对称节点，62% 增加 12 个价值 3 的对称节点，82% 进入终局超频。迁移资源保留相同的 32 个永久节点，另有 8 个价值 3 的临时节点在 0%、25%、50%、75% 使用四批不同位置；临时节点轮换时移除上一批，仅保留当前批。迁移模式不再叠加标准模式的 33%/62% 资源事件，82% 仍统一超频。生成器在开局一次性验证各批位置合法且与永久资源不重合，未来轮换位置仅在迁移模式中公开。

模式划分：

| 模式 | 规则 | 兼容要求 |
| --- | --- | --- |
| 标准控制，2.0 默认 | 沿用持续控制 VP 权重，使用新地图、整数时间与公开前沿 | 所有策略使用同一规则 |
| 迁移资源 | 开局公开列出资源轮换的时点、位置和价值；到时移除上一批临时节点、启用下一批 | 永久资源不移除，资源总价值及时更新，事件记录具体格子变化 |
| 经典 1.0 | 锁定基线地图、18 个基线策略和 .035 步进语义 | 单独规则版本，保留原 URL 配置和旧玩法的复现入口 |

标准控制继续采用：

`VP/s = 10 × (0.65 × 控制面积/可通行面积 + 0.35 × 控制资源价值/当前总资源价值)`

迁移资源也使用同一公式，通过资源位置和保有时间改变竞争重点。规则没有隐藏的追赶奖励或针对「最强」的专属惩罚。资源、地形和攻击信息向所有 Agent 同等公开。

### 4.2 策略生态与算法图鉴

保留全部 18 个已有策略及其明确的“风格/启发式”命名，经典模式冻结原实现。标准模式适配新的通路、资源距离和公开预算，并增加三个有明确实现定义的策略：

1. 路径规划师：在当前公开通行图上实际执行 A*，以资源价值、路径成本和敌占风险选择目标；若仅实现近似距离，名称必须相应改为启发式。
2. 边界调度器：比较扩张、补洞、护点和反抢对接下来 VP 保有的贡献，避免与「最强」仅有不同权重。
3. UCB 策略调度：在几种宏观行动间维护真实计数和均值，按 UCB1 选择；反馈使用可解释的控制收入变化，记录采样与更新过程。

算法图鉴展示适用场景、输入信息、决策方法、预算使用、实际样本表现及一次具体决策。算法名称没有未经数据支持的强度标签。保留「最强」名称与规划器定位，2.0 改进须依赖公共信息和留出样本验证。

生态验收以行为与数据为准：不同代表策略必须表现出可测的路线、保有、进攻或紧凑性差异；只有在批量样本中实际形成优势，界面才将其描述为某种地图或对手的优势策略。

### 4.3 赛事中心

赛事改为正式工作区，保留六种赛制，并明确规模：

| 赛制 | 支持人数 | 关键规则 |
| --- | --- | --- |
| 单循环、双循环 | 4 / 8 / 16 | 每对参赛者一或两次对阵 |
| 淘汰赛 | 4 / 8 / 16 | 标准括号；至少四人时提供季军赛 |
| 瑞士轮 | 4 / 8 / 16 | 可选轮数 1～人数减 1；优先避免重复，再比较积分与种子位距离 |
| 小组赛、小组加淘汰 | 8 / 16 | 每组四人；混合赛每组前二晋级 |

每个对阵可选择 1、3 或 5 张独立种子地图，每张地图交换出生侧打两局，按整个对阵累计 VP 比较胜负。界面称为“地图数”，避免混同为可能提前结束的 BO3/BO5。

新增逐局进度、自动继续赛程、暂停队列、取消待运行任务、恢复未完成赛事、按算法筛选赛果、进入某局回放，以及导入/导出完整赛事包。已经结算的单局以唯一任务 ID 保存，恢复时不重复计分。Worker 内部必须分批让出消息处理机会，长任务期间控制按钮才能生效。

循环和小组继续采用胜 3、平 1、负 0。瑞士轮的同分排序增加 Buchholz，再比较 VP 净胜、累计 VP 与种子位。淘汰完全同分时加赛一张换边地图；仍同分则按文档明确的翻色、终局领地和确定性种子决胜，记录实际使用的决胜理由。

### 4.4 回放、存档与赛后分析

2.0 的回放由初始棋盘、逐 tick 事件账本和棋盘检查点驱动，不要求重新执行旧策略代码。用户可以播放、暂停、逐轮查看、拖动时间轴、跳转资源事件和领先易手，观察同步提交与结算结果。

棋盘检查点每 10 个模拟秒生成一次；资源变化、控制权变化、得分、动作结果和事件按整数 tick 编号保存。拖动时间轴从最近检查点应用增量，回放过程中不调用 Agent，也不消耗比赛 RNG。

运行中存档另存完整引擎状态：时间、棋盘、各随机流、事件标记、所有 Agent 状态和版本。每 5 个模拟秒覆盖保存本局的最新恢复点，暂停及显式保存时再立即保存一次。恢复运行要求引擎和策略版本匹配；历史回放不受此限制。

赛后分析提供可核查指标：领地与资源各贡献多少 VP、各阶段增分、资源保有时长、翻色与反抢、前沿暴露、真实领先易手时刻及双方差距来源。指标从计分账本计算；自述的 `thought` 作为策略说明，不能单凭它认定胜因。精选决策显示当时公开输入、所选动作、有限的备选评分及实际结算。

继续保留离线 HTML、AI 可读 Markdown 和完整 JSON.gz。新增导入自己的 2.0 对局包、赛事包与实验包；导出运行中的比赛时截取一致的逻辑时点，后续比赛不修改该导出。

旧 JSON 格式版本 2 只能迁移其确实包含的终局棋盘、历史统计、事件与决策。旧文件没有完整资源事件位置和 RNG 状态，不能伪装为可恢复的 2.0 存档，也不保证完整棋盘回放。

### 4.5 策略实验室

将已有评测脚本能力带入浏览器。用户可选择参赛策略、地图、时长、种子集和全出生位轮换，查看预计单局数后运行；支持进度、取消、保存和继续。

单挑以同种子换边双局作为一个地图样本；四方以同种子全部出生位的聚合结果作为一个地图样本。分地图、时长、对手和规则版本显示样本胜率、平均排名、平均 VP 差与性能开销。统计按独立地图种子聚合，不能将同地图轮换当作互相独立的样本。

置信区间采用以地图种子为单位的确定性 bootstrap，2000 次重采样；少于 8 个独立种子时只展示描述统计及实际样本量。可展示本地单挑 Elo，固定初值 1000、K=24，并按任务 ID 稳定顺序计算；四方比赛与实时局势估计不混入该评分。

实时榜单保留“当前胜率”，附就近短标签“局势估计”；实验室展示的是实际样本胜率。2.0 不宣称实时估计已完成概率校准。

为「最强」及新策略划分调试种子与冻结后的验证种子。调试样本可以作为回归记录，不能混入宣传用留出结果。所有实验包带完整配置、策略版本、代码摘要、地图与逐局结果。

## 六、时钟、随机流和决策公平性

新引擎使用 20 毫秒整数 tick，每 100 毫秒给各 Agent 一次同步决策机会。事件发生在首次达到公开时间阈值的 tick，记录实际执行时间；模拟结束时不再发放新的决策机会。

每个 tick 的顺序固定：

1. 按上一个边界后的控制状态累积当前时间区间的 VP。
2. 推进整数时间，执行到期的公开资源事件。
3. 若到达决策边界，构造同一张不可变决策快照，收集所有 Agent 动作。
4. 根据快照校验和计算成功率，然后统一解决同格冲突并修改控制权。
5. 更新下一时间区间的统计、事件账本与所需检查点。
6. 到达比赛结束时间时冻结结果并调用策略终局反馈。

地图、动态事件、候选排序、每个参赛者的策略 RNG、攻击结果和同格冲突分离。候选生成不能改变事件或攻击随机流；固定参赛者身份在换边时保持其策略随机流身份。攻击与冲突随机值通过种子、tick 和稳定参与者/目标标识派生，避免遍历顺序改变抽签分配。

公开前沿按目标去重，规范化合法来源，不再按己方面积扫描间隔遗漏边界。策略得到相同字段；公共虚拟前瞻只能假设合法动作成功并重算当前规则，不能读取未来 RNG。

所有策略获得相同动作频率。提供确定性的公共工作预算，计数候选评分、路径节点展开及前瞻展开；记录实际使用量。该计数是算法工作指标，不冒充精确 CPU 时间。真实 `thinkMs` 仍仅作为机器相关性能数据。内置算法必须采用有上限的循环；不在 2.0 引入任意用户代码执行器。

预算预设为快速 4096、标准 8192、深入 16384 个工作单位，默认标准；全场使用同一预设。一次候选评分或路径节点展开计 1 单位，一次虚拟行动结算计 4 单位；所有策略通过同一计数接口消费预算。完整公共前沿不被预算截断，策略自行决定评估顺序。预算耗尽时采用已评估的最佳合法动作；如果一个候选都未评估，选择规范排序中的首个合法动作，空前沿则跳过。异常策略同样采用此确定性回退，并记录原因，回退不得消耗世界 RNG。

标准和迁移模式沿用基线无主格与敌占格的成功率公式、12%～93% 限制、核心保护和终局增加 7.5 个百分点的规则；地图中的不可通行格另作合法性排除。经典模式使用冻结代码，因此保持原始候选来源、随机消费和反馈语义。

## 七、界面与交互

正式工作区分为竞技场、赛事中心、回放分析、策略实验室和算法图鉴。桌面以战场为视觉中心，右侧保留实时榜单和局势；曲线、阶段事件和算法说明拥有固定位置。手机优先战场与开始/暂停操作，其他信息按可切换区域呈现。

设置使用正常文档流中的展开区域，打开后推开下面内容；顶部、收起按钮和全部控件可访问。赛事不再依赖挤在单局界面里的大抽屉。对话框统一管理焦点、Escape 关闭与返回位置，手机控件保持至少 44 CSS 像素的触摸高度。

地图绘制支持选择阵营、领地/资源/地形图层、目标和路径覆盖；资源节点与阵营除颜色外还有标记。面板更新按数据变化或节流发生，避免每一帧重建全部 DOM；静态地形缓存，控制权变化采用脏区域绘制。

VP 曲线初始四方标定保留 `2.5 × 时长`，因此 120 秒起始为 300 VP；单挑初始为 `5 × 时长`。真实得分超过标定后，上限按 1/2/5 的漂亮刻度向上扩展，局内不回缩且从不裁剪数据。播放倍速不影响坐标。图例保留“阵营·算法名”。

CSS 重新建立设计变量、基础组件、场景和断点的明确顺序，消除已有跨模块补丁叠加；只允许可说明的局部 `!important`，不再依赖大批最终覆盖。清理未被入口引用的历史 app 副本，Git 历史保留恢复依据。

## 八、持久化、导入与错误处理

IndexedDB 保存记录索引、逐 tick 账本块、最近恢复点、赛事及实验任务。大记录分块写入，UI 只保留当前视图与必要缓存，完整日志不能永久全部堆积在主线程内存。

旧 `cyber-crickets-tournaments-v1` 的有效记录迁移为只读历史赛事，保留原名称、赛制、参与者与实际赛果；未完赛的旧赛事仍在经典引擎中继续。迁移完成前保留原数据，迁移失败时继续读取旧记录。

导入采用版本和结构校验、数组长度和参与者标识检查、有限数值检查以及完整性摘要。导入的名称与策略文本通过文本节点或现有转义函数渲染。未知版本给出具体原因，不将其当成当前版本继续运行。

存储不可用或容量不足时明确显示保存状态，提供导出当前有效记录；不会在写入失败时显示“已保存”。Worker 返回匹配的 matchId、jobId、requestId 和版本，旧任务的延迟消息不得覆盖新比赛。队列取消和重复结果交付应具有幂等性。

## 九、构建、发布与兼容

引入仅构建阶段使用的 Node 脚本，运行时继续零框架。发布到 `dist/`，只包含运行需要的 HTML、CSS、JS 和版本清单，测试、基准原始数据和未使用入口不进入产物。

构建根据整个运行源码集生成内容摘要，将所有模块和 Worker 放在同一个不可变的 `assets/<buildHash>/` 目录。相对引用继承同一版本路径，入口 HTML 指向该目录；CSS 同样使用该版本路径。一次部署无需手工更新散落在模块内的日期参数。

`build-info.json` 包含产品版本、commit SHA、规则/引擎版本和 buildHash。README 主在线入口保留此前已修正的标准地址，并同步功能、设置、规则、实际算法与发布版本；验收可以使用额外版本参数绕过旧缓存。

GitHub Actions 分离测试/构建与部署职责，PR 和升级分支先测试，`main` 才发布。最终固定流程：

1. 修改实际源码并完成所选 2.0 范围。
2. 运行引擎、持久化、赛事、回放、导出和界面检查，生成版本化静态产物。
3. 核查发布入口、递归模块/Worker/CSS 引用和产物完整性。
4. 同步 README、版本说明与真实验证结果。
5. 推送已核对的提交，确认 Pages 测试、上传、部署全部 success。
6. 在标准在线入口检查 build-info 的 commit/buildHash、桌面/手机功能和真实下载文件。

上线前为当前基线保留明确的发布恢复点。发生发布错误时回退到经过核查的完整版本，不能只回退某一个入口文件。

## 十、验收条件

| 范围 | 发布前必须满足 |
| --- | --- |
| 实质升级 | 三种模式、四种新地图、1v1/四方、21 种策略、四个新增/升级工作区均可实际使用 |
| 经典兼容 | 固定 seed/阵容/轮换/时长的经典结果与基线一致，旧 URL 仍能进入对应模式 |
| 时间与公平性 | 播放倍速、暂停/恢复、帧批次大小和 Worker/协作式运行不改变同配置的 v2 结果 |
| 引擎正确性 | 合法动作、核心保护、同快照结算、资源分母、通路连通、结束时间和 VP 账本均有独立断言 |
| 存档 | 保存并恢复后得到相同完整结果；不同或损坏版本不会静默继续 |
| 回放 | 初始、任意检查点前后、事件与终局的棋盘/比分与原账本一致，拖动不执行算法 |
| 赛事 | 所有规定人数和赛制有效；暂停、恢复、重复消息和刷新后不重复结算 |
| 实验 | 单挑换边、四方全轮换与统计聚合正确，控制样本相关性，显示实际样本量和版本 |
| 报告 | HTML 离线可读，Markdown 含完整规则上下文，JSON.gz 可无损读回；运行中导出具有一致时点 |
| 图表 | 高于初始上限的真实 VP 完整可见，图例明确算法，倍速不影响轴 |
| 交互 | 360×800、390×844、768×1024、1440×1000 四种尺寸检查；无横向溢出，设置可展开/收起，主要操作可达 |
| 性能 | 暂停/切换/队列取消在分批任务间及时响应；对同机器基线报告实际开销，不虚构跨设备 FPS 承诺 |
| 发布 | 新 commit 的 Actions、Pages 和在线版本清单相符，所有运行资源可访问，线上跑通单局、赛事、回放和导出 |

经典兼容、v2 引擎、回放和新赛事规则各自有验证样本。不能用所有新代码通过旧测试替代新增能力的行为检查，也不能仅以测试数量作为验收。

## 十一、实施边界与设计审阅

此次 2.0 的各模块围绕同一比赛数据链建设，可以按引擎与数据、竞技场与策略、回放与赛事、实验与发布四个里程碑集成；这是设计上的依赖顺序，详细任务和执行方式将在设计审阅后形成。

2.0 首发不包含账号、云同步、服务器多人对战、任意用户代码沙箱、付费系统或在任意历史时点改策略的反事实分支。它们需要额外安全、运行或产品边界，会削弱本轮核心闭环的交付。

需要审阅的核心决定只有：是否采用完整竞技平台定位、上述首发范围是否合适、是否同意将经典 1.0 与新 v2 规则分开保存。具体模块名、微观交互和内部实现细节可在这些边界内调整。
