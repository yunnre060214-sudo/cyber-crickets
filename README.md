# 赛博斗蛐蛐 · Cyber Crickets

Cyber Crickets 是一个纯前端的**算法自动对抗与观战模拟器**。四个 Agent 在同一张 64×64 网格地图上争夺领地和资源；玩家负责选择算法、地图种子、比赛时长和出生轮换，开局后不直接操作。最终胜负由整场比赛持续累积的 VP（Victory Points）决定。

**在线试玩：** https://yunnre060214-sudo.github.io/cyber-crickets/

## 1. 核心玩法

地图共有 4096 个格子，每个格子包含地形等级、资源价值、控制方和核心区状态。四个阵营从不同出生角的 3×3 核心区开始扩张，核心永久受保护，因此比赛不存在传统意义上的“消灭对手”。

单局提供 60、90、120、180 秒快捷项，默认 90 秒，并支持 10～1800 秒整数自定义时长；播放速度提供 1×、2×、4× 快捷项，并支持 0.25×～20×、步进 0.25× 的自定义倍速。播放速度只影响现实中的观看速度，不改变相同模拟时间内 Agent 获得的决策次数，也不会改变 VP 产出。

每个 Agent 约每 0.085 个模拟秒决策一次。引擎从该阵营领地边界生成合法候选动作，Agent 根据当前公开决策视图选择一个目标，然后四方动作统一结算。

主界面提供实时地图、累计 VP 曲线、实时排名、局势估计胜率、算法当前思路、重大事件信息流和 Markdown 完整日志导出。实时 VP 曲线下方图例使用“阵营·算法名”的形式显示，例如“红方·最强”，便于在颜色之外直接识别当前策略。实时 VP 曲线的 X 轴跟随实际模拟时长，Y 轴按 `2.5 × 回合秒数` 固定标定，因此 120 秒为 300 VP、180 秒为 450 VP，自定义时长按同一比例扩展；播放倍速不参与坐标轴计算。比赛结束后还会生成最终排名、胜因诊断、领先易手次数和 VP / 领地走势。

## 2. VP 与胜负规则

每秒 VP 为：

```text
VP/s = 10 × (0.65 × AreaShare + 0.35 × ResourceShare)
```

其中：

```text
AreaShare     = 当前控制格数 / 4096
ResourceShare = 当前控制资源价值 / 地图当前资源总价值
```

时间归零时累计 VP 最高者获胜。普通扩张、翻色和抢资源本身不会直接增加额外 VP；它们的意义在于改变后续一段时间的 AreaShare 或 ResourceShare。因此，同样一个资源节点通常越早控制、保持越久，产生的累计收益越高。

资源价值分为 1 和 3。比赛过程中会动态增加资源，资源总价值分母随之更新。

## 3. 行动与成功率

合法动作必须满足：起点是己方控制格；终点与起点上下左右相邻；终点当前不属于己方；终点不是任何阵营的受保护核心。

攻击无主格的基础成功率：

```text
P = 0.93 - 0.12 × (terrain - 1)
```

攻击敌方格：

```text
P = 0.39
  + 0.105 × ownSupport
  - 0.075 × defense
  - 0.05 × (terrain - 1)
```

终局超频阶段再增加 0.075，最终成功率统一限制在 0.12～0.93。所有攻击都基于动作提交前的旧地图快照计算，所有阵营完成选择后统一结算。若多个阵营同轮成功指向同一个格子，则使用确定性的种子随机流选出唯一占领者。

成功动作会得到算法反馈 reward：

```text
reward = 1 + 4 × resourceValue + (原目标属于敌方 ? 0.5 : 0)
失败 reward = -0.15
```

**reward 与 VP 是两个不同概念。** reward 主要服务于 Agent 的反馈或学习逻辑，不直接决定比赛胜负。

## 4. 全局事件

比赛并非静态铺图。三个固定赛程阶段会改变争夺重点：

1. **约 33%：资源潮汐。** 中央区域新增 12 个资源节点。
2. **约 62%：核心节点上线。** 中央 25～38 坐标区域的空格以 9% 概率生成价值 3 的资源。
3. **约 82%：终局超频。** 全体行动成功率模型获得额外 7.5 个百分点，鼓励终局翻色与冲刺。

这些事件对所有阵营同时生效，并写入导出的完整对局日志。

## 5. 实时排名与“当前胜率”

右侧实时排名按当前累计 VP 排序，并显示领地占比、资源价值、翻色次数、当前 VP/s、决策墙钟耗时和 Agent 当前思路。

**当前胜率不是历史 Benchmark 胜率，也不参与比赛结算。** 它是用于观战的实时局势估计：根据当前累计 VP、当前 VP/s、本局截至当前的平均得分速度和剩余比赛时间估算每个阵营的终局竞争力，再通过归一化得到四方合计 100% 的概率分布。开局没有信息时四方均为 25%；比赛结束后，唯一第一名显示 100%，并列第一则均分 100%。

它回答的是“按照现在的比分与控制节奏继续发展，谁更占优势”，不能替代大量独立对局得到的统计胜率。

## 6. Agent 阵容

当前内置 **18 个策略**。部分名称描述算法风格或启发式来源，并不宣称完整实现同名经典算法。

| 显示名称 | 当前决策方式 |
| --- | --- |
| BFS 风格洪流 | 依据邻格连贯性铺开，不执行完整层序遍历 |
| DFS 风格穿刺 | 沿上次成功方向深入，不维护完整深度搜索栈 |
| Greedy 疯狗 | 优先眼前资源、翻色等高即时价值目标 |
| Random 赌徒 | 从合法候选边界随机选择，作为基准线 |
| ACO 风格蚁道 | 成功路径沉积信息素并随时间蒸发 |
| Voronoi 圈地 | 比较己方与敌方核心距离，塑造势力圈 |
| 势场 流体 | 资源形成吸引力，敌方压力形成排斥力 |
| PID 风格稳健 | 根据目标面积与实际面积误差动态调节攻守 |
| Q-Learning 学习者 | 在扩张、进攻、资源、巩固四种宏观动作间进行时序差分学习 |
| 防反启发式 | 估计局部敌压和最坏反击风险，不构造完整 Minimax 博弈树 |
| Monte Carlo 采样 | 固定次数采样评估候选动作，不执行完整 MCTS 树搜索 |
| 资源链启发式 | 朝最近未控制资源推进，不实际生成 MST |
| Frontier Runner | 低阻力优先，以阵型完整度换取铺图速度 |
| Raider 掠袭者 | 优先攻击敌方薄弱边界与孤立格 |
| Turtle 堡垒 | 沿高己方邻接密度区域紧凑扩张 |
| Resource Denial | 优先夺取敌占资源并封锁高价值节点 |
| Momentum 变速器 | 根据面积、敌压和比赛阶段动态改变扩张与进攻权重 |
| **最强** | VP 预测规划器：长局前沿投资、资源保有与护点、紧凑边界回收、去重 Beam 前瞻 |

### 「最强」v6 规划器

v6 的首选策略是**先建立能继续扩张的前沿，接战后回收紧凑边界，把资源变成能保有的收入**。它保留 opening、expansion、contest、final 四阶段和 v5 的止损状态，但修正了几项会误导规划的估值。

- **提前看见反超风险。** 所有 Agent 都统一收到其他阵营当前的公开比分、领地、资源和 VP/s。最强比较各对手的静态终局投影，因此自己暂时排名第一时，也能识别更快的追赶者。投影只是按当前速度外推，不是终局预测保证。
- **长局投资与接战收边。** opening / expansion 的无主前沿价值随绝对剩余时间增加，最高为原权重的 4 倍；接战后提高多条己方邻边的价值，优先补洞和回收容易反推的控制面。
- **资源按 VP 尺度计价。** 使用地图当前资源总量换算资源的边际 VP，结合邻接支援和敌方暴露估计保有时间；同时评估保护受威胁的己方邻接资源。保有时间仍是启发式，不是对手攻击概率的精确模型。
- **准确的两步前瞻。** 首步使用规则固有成功率，不再混入无关动作的成功率 EMA。公共 continuation 通过单格虚拟占领视图更新双方支援、敌压、资源路径与护点信息，不修改实际地图；它不会继续追逐假设中刚拿到的资源。
- **搜索预算用于不同目标。** 在截取 Beam 前按目标格去重，同一个目标的多个合法来源不再挤占搜索名额。每次决策只计算一次阶段与攻守状态，再用于所有候选。

这些改动不改变 VP 公式、行动频率、出生点、同步结算或种子随机机制。新公开字段对所有策略相同，不提供未来随机数或隐藏信息。显示的首步成功率是规则固有概率；同轮争抢一个目标仍可能导致占领失败。

可复现评测脚本为 `scripts/benchmark-strongest.mjs`。使用包含基线提交的完整 Git 历史，在项目根目录执行：

```bash
node scripts/benchmark-strongest.mjs --profile=validation --output=validation.json
node scripts/benchmark-strongest.mjs --profile=regression --output=regression.json
node scripts/benchmark-strongest.mjs --profile=duel --output=duel.json
```

默认与 v5 提交 `5c4aad40bbe7edf0932e51d342a538bcf9cde9ca` 对照，也可以用 `--baseline=<commit>` 指定其他版本。validation 使用调试之外的 3 个种子 × 4 个出生位 × 90/180/400 秒 × 2 组阵容，共 72 局；regression 重跑 `RW2GG2` 的 400 秒四出生位；duel 对另外 17 个策略各进行同种子换边双局，固定参赛者随机流。脚本输出逐局结果、实际源码哈希和本机耗时。固定种子与轮换样本存在相关性，不等同于全局胜率或“必胜”证明。

本轮发布评测与 v5 对照（固定种子样本）：

| 评测 | v5 | v6 |
| --- | ---: | ---: |
| 新种子四方对抗 | 51/72 胜 | 68/72 胜 |
| 原 400 秒败局四出生位 | 1/4 胜 | 3/4 胜 |
| 17 个策略换边单挑 | 15/17 对阵胜 | 17/17 对阵胜 |

原 `RW2GG2` 轮换 0 从第二名 829.66 VP 提升到第一名 1076.92 VP。新种子组仍有 4 个败局，其中 1 局旧版获胜、新版落败；不是必胜保证。方法、败局、源码哈希与逐局数据见[完整评测](docs/benchmarks/strongest-v6.md)。

## 7. 公平性与可复现性

项目使用确定性 PRNG，并为世界和 Agent 派生独立随机流。相同代码版本、相同种子、相同阵容、同时长和相同出生轮换应产生相同地图、决策与结果。

四方模式提供四种出生轮换。同一地图下依次切换轮换，可以让不同 Agent 处于四个出生角，从而降低固定位置偏差。当前单局界面的四角轮换仍需要分别运行，严格算法强度比较应使用大量种子 × 全出生位轮换，而不是只看一局。

界面显示的 `thinkMs` 是浏览器墙钟耗时，只用于性能观察。它不改变 Agent 的行动频率，也没有被当作统一 CPU 预算。Monte Carlo 策略使用固定迭代次数而不是固定墙钟时间。

## 8. 比赛赛程

赛事系统固定使用 8 名参赛 Agent，支持：

- 单循环
- 双循环
- 淘汰赛
- 小组赛
- 瑞士轮
- 小组 + 淘汰赛

赛事单局时长同样支持 60、90、120、180 秒快捷项以及 10～1800 秒自定义值。赛事中的单场对阵采用 **1v1 同种子换边双局**。双方在同一地图种子上各打两局并交换左右出生位置，以累计 VP 决定该对阵结果。循环、小组和瑞士轮使用胜 3 分、平 1 分、负 0 分；同分依次比较 VP 净胜值、累计 VP 和种子位。淘汰赛累计 VP 完全相同时，再依次使用翻色次数、终局领地和固定种子决胜。

赛事计算放在 Web Worker 中执行，避免快速模拟完整赛程时阻塞主界面。赛事记录保存在当前浏览器本地。

## 9. Markdown 完整日志

右侧“实时排名”和赛后报告都可以直接导出 Markdown 日志。日志开头自带完整的游戏模型说明，因此可以直接发送给一个全新 AI 会话分析，无需先解释 Cyber Crickets 是什么。

日志包括：对局元数据、地图种子、出生轮换、Agent 阵容、最终或当前排名、重大事件、逐秒时间序列，以及每一次算法决策的 from/to、目标状态、地形、资源、邻格支援、防守、敌压、算法 thought、成功/失败与 reward。

因此它既可以用于解释“为什么某算法反超”，也可以用于寻找长期策略缺陷、失败目标循环、资源争夺效率和阶段性决策变化。

## 10. URL 参数

当前单局配置会写入 URL：

```text
?seed=<地图种子>&rotation=<0..3>&agents=<四个策略 key>&duration=<10..1800>&speed=<0.25..20>
```

示例：

```text
https://yunnre060214-sudo.github.io/cyber-crickets/?seed=20260927&rotation=1&agents=aco%2Cminimax%2Cqlearn%2Cvoronoi&duration=180&speed=2
```

  markdown.js            AI 可读完整 Markdown 日志

## 12. 本地运行与测试

项目是无框架、无运行时后端的静态网页。

```bash
npm test
python3 -m http.server 8080
```

然后在浏览器访问 `http://localhost:8080/`。

提交到 `main` 后，GitHub Actions 会自动部署到 GitHub Pages。

## 13. 当前定位与后续方向

当前版本的重点是：**可复现的算法观战、明确的持续控制计分、具有差异化行为的 Agent、多轮赛事、完整决策日志和可解释的赛后分析。**

如果用于严格算法 Benchmark，仍建议继续补充：自动多种子 × 四出生位批量测试、置信区间与 Elo/TrueSkill 等统计指标、对称 Benchmark 地图、统一可度量计算预算，以及更完整的对手模型。单局“当前胜率”只是实时局势指标，不应被当成 Agent 的长期统计强度。
